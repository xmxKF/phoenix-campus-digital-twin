# V4 室内、机电与可反馈模拟设计依据

记录日期：2026-09-30。本文是当前项目的概念补全依据，配合 `design-contract.json` 使用。建筑外形沿用三张用户图与 V3 CAD；室内布局、设备数量、管线尺寸、负荷与运行曲线都是本项目可编辑的概念推定。未完成施工机电设计、规范校核或真实设备接入。

## 1. 参考站实际检查到什么

用户参考站 <https://xmxkf.github.io/fab1-digital-twin/> 的首页跳转至 `Web孪生/index_local.html`。2026-09-30 通过只读 HTTP 获取 HTML 和 `app.js`，审查其源代码，副本保存在 `reference-project/`。本研究没有将源码检查描述为浏览器功能实测；父任务另外进行了浏览器查看。

可确认的页面功能：外观/剖切/1F俯视/光刻区、楼层显隐与展开、资产选择、温度和洁净度图层、模拟时钟、投片速度、暂停、故障注入、事件日志和生产指标。页面明确标注模拟数据。

关键区别在于 `app.js` 的离散事件模型：批次释放→选择设备→转运→入队→加工完成→下一工序；设备故障会中断加工、重分配队列，并按模拟维修事件恢复。WIP、完成批次、周期和负荷由这些事件累积，设备状态又驱动场景标记与关联线。这是可操作反馈的有效范例。它不是已验证的真实工厂模型，也不是当前八栋楼的真实数据源。不得把该站的设备数、制造节拍或工艺路线移植成客户事实。

本项目采用同样的**操作→资产→下游依赖→读数/趋势→回执**原则，按楼宇用途另写模拟。按钮变色或独立正弦波不足以表示控制成功。

## 4. 必须可以沿线追踪的拓扑

**电：**园区供给（示意边界）→本楼主配电柜→楼层/区域配电回路→照明、插座、空调、泵及专用设备。强电与弱电线槽分组，不共用一个无含义的装饰线。每个负载记录`circuit_id`；同一回路所有依赖资产断电时应联动，别楼回路不受影响。UPS仅用于明确的示意控制/关键负载，不能声称支持整楼生产。所有断路器额定值与线径留空或标概念值。

**生活水：**水表/边界→隔离阀→立管/分配器→卫生、茶水、厨房冷水支路；热水从示意热源→供水→末端，另有回水→循环泵→热源。冷水蓝、热水红、热回水橙可作为本项目图例，不冒充统一法定色标。

**PCW：**换热边界→循环泵→供水主管→工艺设备→回水主管→换热边界，闭环与生活水不直连。系统图必须看出回程；单向蓝管不能被叫作完整冷却系统。实际补水、处理和隔离设备在本轮边界外。

**排水：**卫生/茶水→排水支路→立管→室外示意出口；厨房含油排水→隔油单元→出口；实验废液标单独待定处理边界，不能直接接生活污水。坡度、存水弯、通气、管径和穿楼板防火未完成工程核验。

**空气：**舒适空调送回风连接房间/设备；厨房罩→油烟支管→风机/处理示意边界，补风另路。实验排风单独标识，不凭一个“AHU”标签混同洁净循环、实验排风和厨房油烟。

## 5. 操作与反馈合同

每个可控资产至少分开 `desired`（请求）、`applied`（模拟执行器接受）、`observed`（模拟反馈），附带时间与质量。操作生成命令ID，先显示待执行，正常延迟后应用，再由反馈确认；离线、断电或卡滞必须显示拒绝/超时/不一致，不可仅切按钮即显示成功。模拟时间暂停时，命令仍可排队，但不在后台偷偷完成。

手动模式保存覆盖值；回自动才恢复场景/计划。报警ACK只设置已确认，不移除活动故障。清除故障表示注入的模拟原因已撤销，恢复仍有执行延迟；复位不能让离线或断电设备瞬间恢复读数。支持关闭配电回路、卡阀、停泵、断通信、漏水等可复现情景。

最低因果链：关灯→灯具发光/状态改变→该回路功率下降；停泵或关阀→流量/压力下降→关联末端受影响；停AHU→送风下降、房间温度随时间偏移；配电跳闸→下游设备不可执行；漏水→本区域耗水异常/报警；ACK→状态已确认但报警原因仍在。所有曲线是简化经验模拟，未用于热负荷、水力、保护或产能计算。

## 6. 核验要求

1. 八栋楼全部有独立房间、至少两类可控资产和可追踪供电/水路关系；实施数量以最终manifest为准。
2. 资产选择能同时定位场景几何、资产ID、依赖回路、反馈读数和事件。
3. 每楼断一个照明回路，只影响正确依赖；FAB1泵故障不改写FAB2；不存在生活水至PCW的跨系统边。
4. 验证正常命令、断电拒绝、卡滞超时、离线质量、报警确认与原因清除、自动/手动、暂停/恢复、趋势与复位可复现。
5. 3D运行表现与模拟状态对应；不能用全局均匀变色代替设备级反馈。帧率优化保持既有树叶几何。

本文件记录设计合同与研究，不是这些条目已全部实现的证明；实现与测试结果由本轮代码、FreeCAD导出和验证记录分别给出。
